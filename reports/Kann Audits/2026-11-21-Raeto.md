# Findings

## Informational

### [I-01] Tokens sent directly to the contract are locked forever

**Severity**

Informational

**Location**

`RaetoStaking.sol#L74-L87`

**Description**

`stake` only credits the tokens that arrive during that call (balance after minus balance before). Tokens sent to the contract any other way are not credited to any wallet:

- RAETO sent with a plain `transfer`;
- any other ERC-20.

The contract has no function that can move this surplus: neither the RAETO above `totalStaked` nor any other token.

**Impact**

- A user who sends RAETO to the contract instead of calling `stake` loses those tokens for good, and so does anyone who sends some other token there by mistake. The only way to recover them is a future upgrade, which goes through the 48-hour process.
- Surplus RAETO also makes `token.balanceOf(contract)` larger than `totalStaked`. Off-chain code that uses the contract's balance as total stake will over-count.

This seems to be a deliberate trade-off: having no recovery function keeps the guarantee that tokens only ever go back to the wallet that staked them.

**Proof of concept**

Foundry; `s` is the proxy cast to `RaetoStaking`, `tok` is the RAETO mock, `alice` is a staker.

```solidity
vm.prank(alice); tok.transfer(address(s), 10e18);
assertEq(s.staked(alice), 0);                 // not credited
assertEq(tok.balanceOf(address(s)), 10e18);   // no function can move it
```

**Recommendation**

If the trade-off is intended, acknowledge it. Off-chain reward logic should use `totalStaked` and `staked(addr)`, never the contract's balance.

If recovery is wanted, an owner-only function can be limited to the surplus, so staked funds stay untouchable:

```solidity
function rescue(IERC20 t, address to) external onlyOwner {
    uint256 amt = t.balanceOf(address(this));
    if (t == token) amt -= totalStaked;   // never touches staked RAETO
    t.safeTransfer(to, amt);
}
```

**Team Response**

Acknowledged. There is deliberately no rescue function, so tokens only ever go back to the wallet that staked them. Raeto's rewards are based on `staked` and `totalStaked`, never on the contract's token balance.

### [I-02] Announced upgrades never expire

**Severity**

Informational

**Location**

`RaetoStaking.sol#L121-L126`, `RaetoStaking.sol#L136-L142`

**Description**

`proposeUpgrade` stores `pendingImplementation` and sets `upgradeReadyAt = block.timestamp + 48 hours`. `_authorizeUpgrade` checks that the time is not *before* `upgradeReadyAt` but sets no latest time. A pending upgrade is only removed when it is executed or when `cancelUpgrade` is called.

**Impact**

An upgrade announced at time T can be executed at any point after T + 48 hours, even months or years later, without a new `UpgradeProposed` event. When it finally runs:

- stakers who joined after the announcement get no fresh notice;
- stakers who assumed an old proposal had been dropped are not warned again.

The 48-hour minimum is always enforced, so no funds are directly at risk.

**Proof of concept**

Foundry; `s` is the proxy cast to `RaetoStaking`, `owner` is the contract owner, `newImpl` is a new `RaetoStaking` implementation.

```solidity
vm.prank(owner); s.proposeUpgrade(address(newImpl));
vm.warp(block.timestamp + 730 days);
vm.prank(owner); s.upgradeToAndCall(address(newImpl), ""); // succeeds, no new announcement
```

**Recommendation**

If the lack of expiry is intended, acknowledge it. Monitoring and the front-end should treat any non-zero `pendingImplementation` as a live upgrade, however old the announcement is.

Optional hardening: reject execution after `upgradeReadyAt + N days`, so a stale announcement has to be made again (with a new 48-hour notice) before it can be used.

**Team Response**

Acknowledged. Raeto will always carry out or cancel an announced upgrade as soon as the 48-hour delay has passed, and will not leave one pending.

### [I-03] `renounceOwnership` is available and permanently disables all owner functions

**Severity**

Informational

**Location**

`RaetoStaking.sol#L25`

**Description**

`RaetoStaking` inherits `renounceOwnership()` from `OwnableUpgradeable` and does not override it, so the owner can call it on the proxy. A normal handover takes two steps (`transferOwnership`, then `acceptOwnership`). `renounceOwnership` takes effect in a single transaction: it sets the owner to `address(0)`, clears `pendingOwner`, and cannot be undone.

**Impact**

After renouncing, every `onlyOwner` function stops working for good: `pause`, `unpause`, `setMaxPerWallet`, `setMaxTotal`, `proposeUpgrade`, `cancelUpgrade` and `upgradeToAndCall` (through `_authorizeUpgrade`). In practice:

- **If the contract is paused at that moment,** `stake` (`whenNotPaused`) reverts forever and the contract can only shrink.
- **If it is not paused,** nobody can pause it in an emergency or change the limits.
- **The contract can never be upgraded,** so bugs can't be fixed. An upgrade already pending can be neither executed nor cancelled.

`unstake` has no owner or pause check, so stakers can always withdraw and no funds are at risk.

**Proof of concept**

Foundry; `s` is the proxy cast to `RaetoStaking`, `owner` is the contract owner, `alice` is a staker.

```solidity
vm.prank(owner); s.pause();
vm.prank(owner); s.renounceOwnership();
vm.expectRevert(); s.unpause();                    // nobody can unpause
vm.prank(alice); vm.expectRevert(); s.stake(1e18); // staking blocked forever
```

**Recommendation**

- **If renouncing is not intended,** override it so it always reverts:

```solidity
error RenounceDisabled();
function renounceOwnership() public pure override { revert RenounceDisabled(); }
```

- **If renouncing is kept on purpose** (for example to make the contract permanently non-upgradeable later), call `unpause` and `cancelUpgrade` first.

**Team Response**

Acknowledged. Raeto will not renounce ownership. If Raeto ever makes the contract permanent, it will first unpause it and cancel any pending upgrade.
