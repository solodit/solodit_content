# Findings

## Medium Risk

### [M-01] OakBurner note spot tolerance widens sandwich slack

**Severity**

Medium

**Location**

`OakBurner.sol#L138-L149`

**Summary**

`OakBurner.buyAndBurn` accepts any signed price note that is within 10 percent of the live OAK/ETH spot and younger than 300 seconds, and it builds the output floor from the note price. A caller who holds a note priced 9 percent below spot gets a floor that is 9 percent lower. Combined with the missing minimum on the first swap leg, this raises the amount a sandwich can take from about 1 percent to about 10 percent of a burn chunk.

**Description**

In `buyAndBurn` (OakBurner.sol L131-165):

```solidity
uint256 oakPerEthE18 = oracle.verifyNote(n, sig, msg.sender);      // L138
uint256 spotOakPerEthE18 = oracle.spotOakPerEthE18();              // L139
uint256 noteSpotTolerance = spotOakPerEthE18 / NOTE_SPOT_TOLERANCE_DENOMINATOR;   // L140, denominator = 10
... if (noteSpotDifference > noteSpotTolerance) revert NoteSpotMismatch(...);     // L143
uint256 minOakOut = OakPricing.burnerMinOut(usdgIn, oakPerEthE18, ethUsdE18, oakDecimals, floorBps);   // L149
```

`minOakOut` is linear in `oakPerEthE18`. The oracle itself only requires the note to lie in [spot/2, spot*3/2] (OakOracle.sol L198, `_insideGuard`), and the burner narrows that to +/-10 percent. Within those bounds the caller chooses which valid note to submit. A note at 0.91 times spot is accepted and lowers `minOakOut` by 9 percent.

Because the first swap leg has no minimum (see L-02), the final OAK floor is the only protection, and the note price sets it. The signature proves that the signer issued the price, not that the price is the fair price at execution time.

Attack path: the caller holds two valid notes for its wallet inside one 300 second window, one near spot and one near the bottom of the band. It submits the low note, front-runs the first swap leg to the new floor, lets the burn execute, and back-runs.

**Impact**

The extra slack is up to about 10 percent of each chunk, taken from USDG meant for buy and burn. The burner holds $5.33 today and the cap is about $308 per call, so the absolute loss is small. Impact grows with the per-call cap.

**Likelihood**

The attack needs a wallet that the hosted signer issues a burner note to. The documentation describes the operator wallet fetching one caller-bound note per burn. Nothing in the repository shows whether the service issues several notes per window, or issues notes to other wallets. If it does not, only the operator holds notes, and the finding reduces to the first-leg sandwich. A compromised signer key would reach the same result without any limit on note count.

contract AmmV3Router is ISwapRouter02 {
    MockToken public usdg;
    MockToken public weth;
    uint256 public rUsdg;
    uint256 public rWeth;
    uint256 public feePpm;

    function init(MockToken usdg_, MockToken weth_, uint256 rUsdg_, uint256 rWeth_, uint256 feePpm_) external {
        usdg = usdg_;
        weth = weth_;
        rUsdg = rUsdg_;
        rWeth = rWeth_;
        feePpm = feePpm_;
    }

    function exactInputSingle(IV3SwapRouter.ExactInputSingleParams calldata p) external payable returns (uint256 out) {
        require(p.tokenIn == address(usdg) && p.tokenOut == address(weth), "pair");
        require(usdg.transferFrom(msg.sender, address(this), p.amountIn), "pull");
        out = _quoteAndMove(true, p.amountIn);
        require(out >= p.amountOutMinimum, "Too little received");
        weth.mint(p.recipient, out);
    }

    function swapExact(address tokenIn, uint256 amountIn) external returns (uint256 out) {
        if (tokenIn == address(usdg)) {
            require(usdg.transferFrom(msg.sender, address(this), amountIn), "pull");
            out = _quoteAndMove(true, amountIn);
            weth.mint(msg.sender, out);
        } else {
            require(weth.transferFrom(msg.sender, address(this), amountIn), "pull");
            out = _quoteAndMove(false, amountIn);
            usdg.mint(msg.sender, out);
        }
    }

    function _quoteAndMove(bool usdgIn, uint256 amountIn) private returns (uint256 out) {
        uint256 inFee = amountIn * (1_000_000 - feePpm) / 1_000_000;
        if (usdgIn) {
            out = rWeth * inFee / (rUsdg + inFee);
            rUsdg += amountIn;
            rWeth -= out;
        } else {
            out = rUsdg * inFee / (rWeth + inFee);
            rWeth += amountIn;
            rUsdg -= out;
        }
    }
}

contract RateV4Router is IUniversalRouter {
    MockToken public oak;
    uint256 public oakPerEthE18;
    uint256 public feeBps;
    uint256 public lastOut;

    function init(MockToken oak_, uint256 oakPerEthE18_, uint256 feeBps_) external {
        oak = oak_;
        oakPerEthE18 = oakPerEthE18_;
        feeBps = feeBps_;
    }

    function execute(bytes calldata commands, bytes[] calldata inputs, uint256) external payable {
        require(commands.length == 1 && commands[0] == bytes1(uint8(0x10)), "commands");
        (, bytes[] memory params) = abi.decode(inputs[0], (bytes, bytes[]));
        V4ExactInputSingleParams memory swap = abi.decode(params[0], (V4ExactInputSingleParams));
        (, uint256 takeMinimum) = abi.decode(params[2], (address, uint256));
        uint256 out = msg.value * oakPerEthE18 / 1e18 * (10_000 - feeBps) / 10_000;
        uint256 minimum = uint256(swap.amountOutMinimum) > takeMinimum ? uint256(swap.amountOutMinimum) : takeMinimum;
        require(out >= minimum, "Too little received");
        lastOut = out;
        oak.mint(msg.sender, out);
    }
}

        uint256 id = vm.snapshotState();
        AmmV3Router pool = AmmV3Router(SWAP_ROUTER_02);
        uint256 wethBought;
        if (attackUsdg != 0) {
            usdg.mint(attacker, attackUsdg);
            vm.startPrank(attacker);
            usdg.approve(address(pool), attackUsdg);
            wethBought = pool.swapExact(address(usdg), attackUsdg);

        internal
        returns (uint256 maxAttack, Outcome memory best, uint256 bestAttack)

        uint256 lo;
        uint256 hi = reserveUsdg * 4;
        for (uint256 i; i < 40; ++i) {
            uint256 mid = (lo + hi) / 2;
            if (_scenario(mid, noteOakPerEth, chunk).ok) lo = mid;
            else hi = mid;

        maxAttack = lo;
        best = _scenario(0, noteOakPerEth, chunk);
        best.attackerPnl = type(int256).min;
        for (uint256 k = 1; k <= 20; ++k) {

            Outcome memory o = _scenario(a, noteOakPerEth, chunk);
            if (o.ok && o.attackerPnl > best.attackerPnl) {
                best = o;
                bestAttack = a;
            }
        }

        internal
        returns (PriceNote memory note, bytes memory signature)

        signature = abi.encodePacked(r, s, v);
    }

    function _poolId(address token) internal pure returns (bytes32) {
        return keccak256(abi.encode(address(0), token, uint24(0), int24(200), PONS_HOOK));

    function test_POC2_LowNoteWidensSlackBy9Percent() public {
        uint256 reserveUsdg = 2_000_000e6;
        uint256 chunk = 20_000e6;
        _initPools(reserveUsdg, 2_000e18);
        oracle.setLiquidityUsdgE6(chunk * 200);

        (, Outcome memory atSpot,) = _bestAttack(OAK_PER_ETH, chunk, reserveUsdg);
        uint256 lowNote = OAK_PER_ETH * 91 / 100; // inside the burner's 10% spot tolerance
        (, Outcome memory atLow,) = _bestAttack(lowNote, chunk, reserveUsdg);

        console.log("loss at spot note (bps):", (base.oakOut - atSpot.oakOut) * 10_000 / base.oakOut);
        console.log("loss at 0.91x note (bps):", (base.oakOut - atLow.oakOut) * 10_000 / base.oakOut);
        console.logInt(atSpot.attackerPnl);
        console.logInt(atLow.attackerPnl);

        assertTrue(atLow.ok, "burner accepts a note 9% below spot");
        assertGt(atLow.attackerPnl, atSpot.attackerPnl * 3, "the extractable value is several times larger");
        assertGt((base.oakOut - atLow.oakOut) * 10_000 / base.oakOut, 900, "more than 9% of the burn is lost");
    }

**Recommendation**

Do not let the note lower the floor below what the live price supports. Use the larger of the note price and the live spot when building the floor:

```solidity
uint256 priceForFloor = oakPerEthE18 > spotOakPerEthE18 ? oakPerEthE18 : spotOakPerEthE18;
uint256 minOakOut = OakPricing.burnerMinOut(usdgIn, priceForFloor, ethUsdE18, oakDecimals, floorBps);
```

Also narrow `NOTE_SPOT_TOLERANCE_DENOMINATOR` so the allowed distance is no larger than the intended floor margin, and have the signer issue at most one note per wallet per window.

**Team Response**

Fixed.

A note up to 10% below spot passed the spot check and lowered the output floor by the same fraction. On a fork that exposed up to 10.7% of a chunk, about 24.75 USDG per full chunk, while the burner held 5.33 USDG. Fixed: the floor now uses the higher of the note price and live spot.

### [M-02] OakBurner floor uses the 30-minute TWAP while leg 1 trades at the live price

**Severity**

Medium

**Location**

`OakBurner.sol#L149`, `OakOracle.sol#L162-L174`

**Summary**

`OakBurner.buyAndBurn` builds its output floor from a 30 minute ETH/USD average (`OakOracle.ethUsdE18`) but executes the first swap leg at the live pool price. When live ETH is below the average the floor is looser than it should be and a sandwich can take the difference. When live ETH is above the average an honest burn reverts until the average catches up.

**Description**

`minOakOut` (OakBurner.sol L149) uses `ethUsdE18`, which `OakOracle` reads as a 1800 second tick average from the ETH/USDG v3 pool (OakOracle.sol L162-174). The first swap leg converts USDG to WETH at the live price of that same pool.

Let `P_twap` be the average and `P_live` the live price in USD per ETH.

- If `P_live < P_twap` (ETH fell): the burner receives more ETH per USDG than the floor assumes. The floor is lower than the honest output by the lag, so a searcher can take that margin on top of the normal slack.
- If `P_live > P_twap` (ETH rose): the burner receives less ETH than the floor assumes, and when the lag exceeds the fee margin (about 1.9 percent at the maximum floor) the honest burn reverts with `TooLittleOak`.

The contracts do not compare the average with the live price of the pool, and the chain has no sequencer feed. After a sequencer outage the average can lag for the full window.

**Impact**

The extra slack equals the lag between the average and the live price, bounded by the market move in 30 minutes. The funds at risk are the burner's USDG per chunk. The rise case only delays burns. No user funds are affected.

**Likelihood**

It needs a fast ETH move (about 5 percent in 30 minutes for the loosening case, about 2 percent for the blocking case) during a burn, and for the loosening case an attacker who can order a transaction ahead of the operator.

### [L-01] OakOracle chunk cap follows manipulable in-range liquidity

**Severity**

Low

**Location**

`OakOracle.sol#L202-L226`, `OakBurner.sol#L135-L136`

**Summary**

The per-call burn cap in `OakBurner.buyAndBurn` is `oracle.liquidityUsdgE6() / 200`, and `liquidityUsdgE6` reads the pool's current in-range liquidity from one PoolManager storage word. Anyone can change that word inside one transaction by adding or removing liquidity, because the Pons hook has no liquidity hooks. The cap is therefore not a fixed spending limit. It amplifies the first-leg sandwich (L-02) and the TWAP lag (M-02) findings.

**Description**

`OakOracle.liquidityUsdgE6` (OakOracle.sol L202-226), in the READY phase:

```solidity
uint160 sqrtPriceX96 = _readSqrtPrice();
bytes32 liquiditySlot = bytes32(uint256(spotStorageSlot) + 3);
uint128 liquidity = uint128(uint256(_readPoolWord(liquiditySlot)));
uint256 virtualEthWei = Math.mulDiv(uint256(liquidity), Q96, sqrtPriceX96);
return Math.mulDiv(virtualEthWei, ethUsd, ETH_USD_SCALE) * 2;
```

The value depends on the live `liquidity` word, which is the liquidity of the current tick only. `buyAndBurn` then enforces `usdgIn <= maximum` (L135-136).

The hook address `0xE5e7...e044` encodes BEFORE_INITIALIZE, AFTER_SWAP and AFTER_SWAP_RETURNS_DELTA only (low 14 bits 0x2044). There are no add-liquidity or remove-liquidity hooks, so nothing in the pool restricts who may add liquidity.

Two consequences:

1. A liquidity provider who adds liquidity in range before the call raises the cap. The cap scales one to one with the word.
2. When the price is moved outside every position, the word is zero, the cap is zero, and every `usdgIn > 0` reverts with `ChunkTooLarge`.

The documentation says the cap is "not a fixed spending cap" (docs/security.md, section 6), so the behavior is acknowledged. This report adds the measurement of its effect on the sandwich findings.

**Impact**

Impact is Low. The cap does not let an attacker force a larger burn: the operator chooses `usdgIn`. The cap only sets the largest chunk the burner will accept. A larger accepted chunk raises the absolute loss in the first-leg sandwich. The zero-liquidity case is a temporary denial of service that costs the attacker capital and is undone by arbitrage.

**Likelihood**

Likelihood is Medium that the cap can be moved, since the hook allows it and it needs only capital. Likelihood is Low that this causes a loss, since the operator chooses the chunk and an attacker must also be ordered around the burn.

### [L-02] OakBurner first swap leg has no minimum output

**Severity**

Low

**Location**

`OakBurner.sol#L225-L240`, `OakBurner.sol#L149-L159`

**Summary**

`OakBurner._swapUsdgForWeth` passes `amountOutMinimum: 0` and `sqrtPriceLimitX96: 0` to the Uniswap v3 router. The only output check is on the final OAK balance delta, whose floor is 96.07 percent of a note-derived value. A searcher who moves the USDG/WETH pool before the burn and restores it afterwards keeps the difference, about 1.5 to 1.9 percent of each burn chunk, taken from the USDG that is meant to buy and burn OAK.

**Description**

`buyAndBurn` (OakBurner.sol L131-165) computes one end-to-end floor:

```solidity
minOakOut = usdgIn * 10^(oakDecimals-6) * oakPerEthE18 * floorBps / (ethUsdE18 * 10000)     (L149, OakPricing.burnerMinOut)
```

`floorBps = min(9607, 10000 - hookFeeBps - creatorTaxBps - 150)`. With the live launch policy (hook fee 100 bps, creator tax 100 bps) the floor is 9607. The honest output after the real 2 percent of pool fees is about 98 percent of the fair value, so a gap of about 1.9 percent is permitted by design.

The first leg `_swapUsdgForWeth` (L225-240) enforces nothing:

```solidity
amountOut = ISwapRouter02(SWAP_ROUTER_02).exactInputSingle(
    IV3SwapRouter.ExactInputSingleParams({
        tokenIn: address(usdg), tokenOut: WETH, fee: V3_FEE, recipient: address(this),
        amountIn: amountIn, amountOutMinimum: 0, sqrtPriceLimitX96: 0 }));
```

`minOakOut` depends on `usdgIn`, the note price and the 30 minute ETH/USD average. It does not depend on `ethOut`. Any WETH amount above zero lets the second leg run, and the burn passes as long as the final OAK amount reaches the floor. The check on `oakOut` at L159 is the only protection.

Attack path:

1. The operator submits `buyAndBurn(usdgIn, note, sig)`.
2. A searcher front-runs with a USDG to WETH swap in the 0.01 percent v3 pool, moving the price against the burner. The size is chosen so that the final OAK amount still reaches `minOakOut`.
3. The burner swaps USDG for WETH at the worse price, then WETH for OAK, and burns less OAK than an honest burn.
4. The searcher back-runs by selling the WETH. The net profit is the burner's extra loss minus the two 0.01 percent pool fees.

The documentation states that this is an output floor and not a price limit (docs/security.md, section 6), so the behavior is known. The finding is the size of the leak: it is not bounded by a fixed amount, it scales with the per-call cap.

**Impact**

Impact is Low. The loss is capped by the floor at about 1.5 to 1.9 percent of each chunk. The burner currently holds $5.33 and the per-call cap is about $308, so the leak today is a few dollars. It grows with OAK pool liquidity because the cap is liquidity divided by 200. The funds at risk are the 25 percent of Oak income that is meant to buy back and burn OAK. No user funds and no protocol solvency are affected.

**Likelihood**

Likelihood is Low. The searcher must be ordered ahead of the operator's call, and Robinhood Chain may not expose a public mempool. At the live cap of $308 the sandwich is unprofitable: the POC shows a loss of $2 for the attacker. It becomes profitable at chunks of about $30k and above. Those chunks need a larger OAK pool, or inflated in-range liquidity (see L-01).

    function exactInputSingle(IV3SwapRouter.ExactInputSingleParams calldata p) external payable returns (uint256 out) {
        require(p.tokenIn == address(usdg) && p.tokenOut == address(weth), "pair");
        require(usdg.transferFrom(msg.sender, address(this), p.amountIn), "pull");
        out = _quoteAndMove(true, p.amountIn);
        require(out >= p.amountOutMinimum, "Too little received");
        weth.mint(p.recipient, out);
    }

    function swapExact(address tokenIn, uint256 amountIn) external returns (uint256 out) {
        if (tokenIn == address(usdg)) {
            require(usdg.transferFrom(msg.sender, address(this), amountIn), "pull");
            out = _quoteAndMove(true, amountIn);
            weth.mint(msg.sender, out);
        } else {
            require(weth.transferFrom(msg.sender, address(this), amountIn), "pull");
            out = _quoteAndMove(false, amountIn);
            usdg.mint(msg.sender, out);
        }
    }

    function _quoteAndMove(bool usdgIn, uint256 amountIn) private returns (uint256 out) {
        uint256 inFee = amountIn * (1_000_000 - feePpm) / 1_000_000;
        if (usdgIn) {
            out = rWeth * inFee / (rUsdg + inFee);
            rUsdg += amountIn;
            rWeth -= out;
        } else {
            out = rUsdg * inFee / (rWeth + inFee);
            rWeth += amountIn;
            rUsdg -= out;
        }
    }
}

### [L-03] `_disarmSweepAfterBurn` Tracks Per-Call `usdgIn` Rather Than Cumulative Burns and Caps Disarm Threshold at Live `maximum`

**Severity**

Low

**Location**

`OakBurner.sol#L167-L178`, `OakBurner.sol#L191-L204`

**Description**

```solidity
function _disarmSweepAfterBurn(uint256 usdgIn, uint256 maximum) private {
    if (armedAt == 0) return;
    uint256 armedBalance_ = armedBalance;
    uint256 minimumDisarmAmount = armedBalance_ / SWEEP_DISARM_DENOMINATOR;
    if (armedBalance_ % SWEEP_DISARM_DENOMINATOR != 0) ++minimumDisarmAmount;
    if (minimumDisarmAmount > maximum) minimumDisarmAmount = maximum;
    if (usdgIn >= minimumDisarmAmount) {
        armedAt = 0;
        armedBalance = 0;
        emit SweepDisarmed(0);
    }
}
```

1. **Dust disarm when `maximum` is temporarily small:** Because `minimumDisarmAmount` is capped at `maximum` (`oracle.liquidityUsdgE6() / 200`), if pool liquidity drops (or is momentarily low at the active tick per L-01) such that `maximum == 10` USDG, a single `buyAndBurn(10, ...)` call burning 10 USDG disarms the 90-day sweep timer for the entire `armedBalance` (e.g. 10,000,000 USDG).
2. **Full balance burn without disarming:** Because `_disarmSweepAfterBurn` evaluates `usdgIn` per call rather than cumulative USDG burned since `armedAt`, executing multiple burns each of size `minimumDisarmAmount - 1` can spend 100% of `OakBurner`'s USDG while leaving `armedAt` and `armedBalance` non-zero.

### [L-04] Owner can zero price signer then sweep burner and redirect payees

**Severity**

Low

**Location**

`OakOracle.sol#L232-L236`, `OakBurner.sol#L167-L204`, `OakSubscription.sol#L277-L282`

**Summary**

The owner can set the oracle price signer to `address(0)`, arm the burner sweep, and then nobody can disarm the sweep. After 90 days `sweepStuck` moves the whole armed USDG balance to the owner. The only disarm path is a successful `buyAndBurn`, which always needs a note signed by the signer the owner just removed. Separately, `setPayees` redirects the 25 percent burn share of the next subscription payment instantly. Both steps need the owner key only.

**Description**

Relevant code:

- `OakOracle.setPriceSigner` (OakOracle.sol L232-236) is `onlySafe`, takes effect at once, and has no zero-address check (the constructor rejects zero at L115-118).
- `OakOracle.verifyNote` (L192-195) reverts with `NoteBadSignature` whenever `priceSigner == address(0)`.
- `OakBurner._disarmSweepAfterBurn` (L167-178) is called only at the end of `buyAndBurn` (L163), so a sweep is disarmed only by a burn.
- `OakBurner.armSweep` (L181-188) and `sweepStuck` (L191-204) are `onlySafe`; after `SWEEP_DELAY` of 90 days the sweep transfers `min(balance, armedBalance)` USDG to `safe`.
- `OakSubscription.setPayees` (L277-282) is `onlySafe`, instant, and `_settle` (L476-478) sends the burn share to whatever `burner` is set to.

The documented protection is: "one permitted maximum chunk can always disarm a working burner" (docs/security.md, section 5). That holds only while the signer signs. Zeroing the signer makes every burn revert, so the protection disappears, and the 90 day timer becomes the only delay. Users have no function to stop the sweep.

Sequence: (1) owner calls `armSweep`; (2) owner calls `setPriceSigner(address(0))`; (3) any `buyAndBurn` reverts with `NoteBadSignature`; (4) after 90 days owner calls `sweepStuck` and receives the armed balance.

The docs state that the owner can replace the signer ("zero address pauses pricing") and can arm the sweep, and that this authority is not limited to a broken burner. The finding is that the two powers combine so that the one safeguard described for the sweep can be removed by the same key.

**Impact**

Impact is Medium for the funds in the burner and the burn share, and no user wallet funds are affected. The armed balance is the USDG set aside for buy and burn (25 percent of income). The burner holds $5.33 today, so the live exposure is small, but the mechanism applies to whatever balance is armed. The `setPayees` part moves only the burn share of future payments, and the other 75 percent already goes to the treasury, which is the owner address in the live deployment.

**Likelihood**

Likelihood is Low. It needs the owner key to act against the project's stated purpose, or the key to be compromised. The key is a single plain key (no code, nonce 0 on the live chain), so key compromise is the realistic path. The 90 day delay gives a visible on-chain window, but nothing in the contracts lets anyone use it.

### [L-05] Subscribers with more than 60 days prepaid cannot migrate to a new OakSubscription

**Severity**

Low

**Location**

`OakSubscription.sol#L395-L414`, `OakSubscription.sol#L513-L519`

**Summary**

`OakSubscription._prepareGrandfathering` computes the carried-over expiry with `_nextPaidUntil(source.paidUntil(wallet))`. That function adds a 30 day period and then reverts with `PrepayCapExceeded` if the result is more than 90 days from now. The predecessor lets a wallet prepay to 90 days. Any wallet with more than 60 days left on the predecessor cannot migrate, and loses the grandfathered terms if the claim window closes first.

**Description**

`_prepareGrandfathering` (OakSubscription.sol L395-414) ends with:

```solidity
return _nextPaidUntil(sourceSubscription.paidUntil(wallet));
```

`_nextPaidUntil` (L513-519):

```solidity
uint256 base = currentPaidUntil > block.timestamp ? currentPaidUntil : block.timestamp;
uint256 nextPaid = base + PERIOD;                 // PERIOD = 30 days
uint256 cap = block.timestamp + PREPAY_CAP;       // PREPAY_CAP = 90 days
if (nextPaid > cap) revert PrepayCapExceeded(nextPaid, cap);
```

For a wallet whose predecessor `paidUntil` is T + 90 days (the maximum the predecessor allows), at time T + 1 day: `base = T + 90d`, `nextPaid = T + 120d`, `cap = T + 91d`. The call reverts. It succeeds only once the inherited time has fallen to 60 days or less, that is from T + 30 days. `setGrandfatherRoot` accepts a deadline from one second to 120 days ahead (L267). If the owner picks a window shorter than 30 days, such a wallet can never migrate.

The same cap is correct for fresh subscriptions, where `base` starts at the current time. It was applied unchanged to inherited time.

**Impact**

Impact is Low. A wallet that cannot migrate loses the grandfathered terms (the same OAK count and no signup burn) and must subscribe again at current terms. No funds are lost. The population is wallets with more than 60 days prepaid on the predecessor.

**Likelihood**

Likelihood is Low. The deployed contract at `0x5e0d...` has `previous = 0`, no root, and holds no USDG, and the docs call it unused, so today no wallet is affected. The bug applies whenever a successor with a lineage is deployed and the predecessor has prepaid users.

### [L-06] Price note has no ordering and subscription guard is 50 percent

**Severity**

Low

**Location**

`OakOracle.sol#L182-L200`, `OakOracle.sol#L240-L246`, `OakSubscription.sol#L383-L392`

**Summary**

A signed price note has no ordering and does not commit to an amount or a plan. `OakSubscription` accepts any note within 300 seconds whose price is within 50 percent of spot (the burner uses 10 percent). A subscriber who holds several notes, or an older note, can pick the one that needs the fewest OAK. Across the allowed band the required OAK count for the same entry price varies by about 2.9 times, and a 299 second old note after a 50 percent price rise needs a third less OAK.

**Description**

`OakOracle.verifyNote` (OakOracle.sol L182-200) checks the wallet binding, a 300 second window, the signature, and `_insideGuard(note, spot)`, which allows `[spot/2, spot * 3/2]` (L198, L240-246). It returns the note price. `OakSubscription._readyPricing` (L383-392) uses that price directly: `oakUsd = ethUsd * 1e18 / oakPerEth`, then market cap, entry price and `requiredCount` (ceil of entry / oakUsd). A lower note price raises `oakUsd` and lowers the count. Nothing makes a newer note supersede an older one: the single-use nonce is chosen by the signer, and the wallet can hold several unused nonces at once. The signer proves the price was issued, not that it is the best price at execution time.

Two ways to use this:

1. Hold several notes in one window and pick the one at the bottom of the band.
2. Keep a note until the market moves up and use it up to 300 seconds later.

**Impact**

Impact is Low. A subscriber locks fewer OAK than the stated pricing curve intends. The holder plan still costs $9 per period. The effect is a weaker OAK lock, bounded by the guard band, and no direct fund loss.

**Likelihood**

Likelihood is Low. It needs the hosted signer to issue more than one note per wallet per window, or to issue notes at different prices. Nothing in the repository shows what the service does. A compromised signer key removes the limit.

### [I-01] Live chunk cap makes the one-chunk sweep disarm amount unstable

**Severity**

Informational

**Location**

`OakBurner.sol#L131-L136`, `OakBurner.sol#L167-L178`, `OakOracle.sol#L202-L226`

**Description**

The documented guarantee that "one permitted maximum chunk can always disarm" is difficult to exercise when `ceil(armedBalance / 100) > maximum`. In that state, the disarm threshold is exactly `maximum = oracle.liquidityUsdgE6() / 200`, and a burn must pass an exact `usdgIn` chosen before the transaction is mined.

The maximum is read live inside `buyAndBurn()`. It changes with OAK/ETH spot, active-tick liquidity, and the ETH/USD 30-minute average:

- If the maximum falls below the chosen amount, the call reverts with `ChunkTooLarge`.
- If it rises above the chosen amount, the burn succeeds and spends USDG, but remains below the new disarm threshold. The old sweep timer remains armed.

A small pool change can therefore defeat an operator's attempt to use the promised one-chunk disarm. This is a liveness and operational reliability issue; the operator can retry, and the caller still chooses the burn amount.

**Recommendation**

Support an explicit "burn the current maximum" mode (for example, `type(uint256).max` as a sentinel) that clamps the requested amount to the live maximum before computing any downstream minimum or executing a swap. This avoids silently reducing an ordinary exact-amount request. Alternatively, allow a defined tolerance below the live maximum to disarm.

Related: L-01 discusses manipulation of the live liquidity-based cap; this finding concerns the exact-amount disarm condition.

**Team Response**

Fixed.

When 1% of the armed balance exceeds the cap, the threshold equals the live cap. A burn sized to the cap seen off-chain then either reverts with `ChunkTooLarge` or spends without disarming. In our test a retry at the current cap disarmed, so the cost is one extra transaction and no USDG is lost. Fixed: the threshold no longer depends on the live cap (see L-03). The trade-off is that a burn disarms only at 1% of the armed balance or when it uses up the armed amount, while smaller burns reduce what a sweep can take.

### [I-02] `OakOracle.spotOakPerEthE18()` Hardcodes `1e18` Scaling While `OakBurner` Accepts `oakDecimals` in `[6, 77]`

**Severity**

Informational

**Location**

`OakOracle.sol#L176-L180`, `OakBurner.sol#L114-L118`

**Description**

`OakBurner` accepts `oakDecimals_` in the range `[6, 77]` and passes `oakDecimals` to `OakPricing.burnerMinOut(usdgIn, oakPerEthE18, ethUsdE18, oakDecimals, floorBps)`. However, in `OakOracle.spotOakPerEthE18()`:

```solidity
function spotOakPerEthE18() public view returns (uint256 value) {
    if (phase() != READY) revert NotReady();
    value = _scaledSquare(_readSqrtPrice(), OAK_ETH_SCALE);
    if (value == 0) revert OracleUnreadable(poolManager);
}
```

In the Uniswap v4 pool where `currency0 = address(0)` (18 decimals) and `currency1 = oakToken` (`oakDecimals` decimals):

```solidity
(sqrtPriceX96^2 / 2^192) = (OAK_human * 10^oakDecimals) / (ETH_human * 10^18)
```

Multiplying by `OAK_ETH_SCALE` (`10^18`) cancels the `10^18` ETH denominator and returns a value scaled by `10^oakDecimals`, **not** `10^18`. If `oakDecimals != 18`:

- If `n.oakPerEthE18` is scaled by `10^18`, `verifyNote` (`_insideGuard`) and `OakBurner` (`NoteSpotMismatch`) will revert because `spotOakPerEthE18()` is scaled by `10^oakDecimals`.
- If `n.oakPerEthE18` is instead scaled by `10^oakDecimals` to pass `verifyNote`, then `OakPricing.burnerMinOut` will miscalculate `minOakOut` by a factor of `10^(oakDecimals - 18)`.

*(Note: On Robinhood Chain, production OAK is deployed with 18 decimals, making this latent in the primary deployment).*

**Proof of concept**

```text

```

**Recommendation**

Either restrict `OakBurner` strictly to `oakDecimals_ == 18`:

```solidity
if (oakDecimals_ != 18) revert InvalidOakDecimals(oakDecimals_);
```

or normalize `OakOracle.spotOakPerEthE18()` by `10 ** oakDecimals`.

**Team Response**

Fixed.

`spotOakPerEthE18` has E18 meaning only for an 18-decimal OAK. For a 6-decimal token an E18 note fails the guard, and a note in the oracle's scale rounds the burner floor to zero. The deployed OAK and burner both use 18 decimals, so nothing deployed is affected. Fixed: `OakBurner` now requires an 18-decimal OAK.

### [I-05] OakBurner spot displacement can revert buyAndBurn

**Severity**

Informational

**Location**

`OakBurner.sol#L138-L143`, `OakOracle.sol#L176-L180`

**Summary**

`OakBurner.buyAndBurn` reverts with `NoteSpotMismatch` when the signed note differs from the live OAK/ETH spot by more than 10 percent. The spot is read from the pool's `slot0` in the same transaction. A griefer who moves the thin OAK pool by about 9 percent immediately before the call makes that burn revert. On the live OAK pool this costs about $1,500 of capital and about $60 of fees per attempt.

**Description**

`buyAndBurn` (OakBurner.sol L138-143) compares the note with `oracle.spotOakPerEthE18()`, which `OakOracle` reads from the v4 PoolManager storage word of `slot0` (OakOracle.sol L176-180, L296-299). The word moves with any swap earlier in the same block or transaction. The burner has no time-weighted reference for the OAK price.

The check exists to catch a bad signed price. It also converts any cheap spot move into a reason for the call to fail. The OAK pool is small: the oracle reports about $61.6k of liquidity, so the ETH side of the virtual reserve is about $30.8k (about 15 ETH). Buying about 4.9 percent of that side lowers OAK per ETH by about 9.1 percent, which is past the 10 percent test against a note signed at the old spot.

The note is not consumed on revert (`noteUsed` is written only after the check passes, and a revert undoes it), so the operator can retry, but every retry can be preempted again at the same cost.

**Impact**

Impact is Low. The effect is a delay of one burn per preempted attempt. No funds are lost and the griefer pays real fees. The signer's note follows the pool, so a displacement that is held for a long time does not block burns permanently.

**Likelihood**

Likelihood is Low. The griefer must be ordered ahead of the operator's transaction on every attempt. The cost per attempt is about 4 percent of the capital used (2 percent each way in hook fee and creator tax) and the capital is returned, so a patient griefer can repeat it. Robinhood Chain may not offer a public mempool.

Acknowledged. Moving OAK spot more than 10% before the call makes `buyAndBurn` revert with `NoteSpotMismatch`; nothing is spent, the note is not consumed, and the operator retries. ### [I-06] `OakOracle.phase()` Queries External Factory Prior to Checking `readyLatched`, Causing DoS if Factory Fails

**Severity**

Informational

**Location**

`OakOracle.sol#L146-L150`

**Description**

`OakOracle.syncPhase()` allows anyone to latch `readyLatched = true` once the pool graduates. However, `OakOracle.phase()` executes `(bool readable, uint8 p,) = _launchRecord()` first before checking the latch:

```solidity
function phase() public view returns (uint8) {
    (bool readable, uint8 p,) = _launchRecord();
    if (!readable) revert OracleUnreadable(ponsFactory);
    return readyLatched || p == 2 ? READY : CURVE;
}
```

If the external `ponsFactory` becomes unreadable, reverts, or returns corrupted data, `phase()` reverts with `OracleUnreadable(ponsFactory)` even if `readyLatched == true`. Because `OakBurner.buyAndBurn` invokes `oracle.syncPhase()` (which evaluates `phase()`), all buy-and-burn functionality is permanently disabled by an external dependency failure that the latch was specifically intended to decouple.

**Recommendation**

Check `readyLatched` before executing the external staticcall:

```diff
 function phase() public view returns (uint8) {
+    if (readyLatched) return READY;
     (bool readable, uint8 p,) = _launchRecord();
     if (!readable) revert OracleUnreadable(ponsFactory);
-    return readyLatched || p == 2 ? READY : CURVE;
+    return p == 2 ? READY : CURVE;
 }
```

**Team Response**

Acknowledged.

Acknowledged. After the latch, unreadable factory data still makes `phase()` revert. That is deliberate fail-closed behavior after a Pons factory outage, and existing tests pin it; the suggested change would also accept unknown phase data as READY. No USDG is stuck, because `armSweep` and `sweepStuck` do not depend on `phase()`. We are keeping the behavior, and it is now documented.

### [I-07] Burns depend on operator-issued notes with no permissionless fallback

**Severity**

Informational

**Location**

`OakBurner.sol#L131-L165`, `OakOracle.sol#L182-L200`, `OakOracle.sol#L232-L236`

**Description**

There is no fully permissionless path to burn the burner's USDG. Every `buyAndBurn()` call needs a fresh caller-bound note from the hosted price signer. The Safe can replace that signer or set it to zero, and the hosted service can withhold notes. In either case, otherwise willing callers cannot disarm an armed sweep through a burn. After 90 days, the Safe can sweep the armed USDG. The timer is the on-chain delay on this owner-controlled path.

This is an authority and availability disclosure, not an unprivileged fund-withdrawal exploit. The single-owner power and zero-signer pause are documented in `docs/security.md`.

There is also a converse trust assumption: if the hosted signer issues burner notes to arbitrary contract wallets, a contract holding its own valid note can order pool trades around its `buyAndBurn()` call in one transaction. The final output floor and 10% note-to-spot check constrain the result; practical profit is not established here.

**Recommendation**

State explicitly in user-facing documentation who can receive burner notes, who can pause them, and that there is no permissionless fallback. If note issuance is intentionally restricted to the operator, document and enforce that policy off-chain.

Related: L-04 discusses owner pause and sweep; I-08 reports the intentionally supported zero-signer pause.

**Team Response**

Acknowledged.

Acknowledged. There is no permissionless burn path: every burn needs a note bound to the caller, a zero signer stops all burns, and the owner's 90-day sweep is then the only way out for armed USDG. Since 16 November 2026, burner notes are issued only to the operator wallet, which also removes the case of a third-party contract trading around its own burn. The owner can pause burns by zeroing the signer, and with the L-04 fix anyone can then flag that change, which voids any armed sweep. The documentation now states who receives burner notes, who can pause them, and that there is no permissionless fallback.

### [I-08] `OakOracle.setPriceSigner` Lacks Zero-Address Validation Causing Permanent DoS to `buyAndBurn`

**Severity**

Informational

**Location**

`OakOracle.sol#L232-L236`, `OakOracle.sol#L192-L195`

**Description**

`OakOracle.constructor` enforces `priceSigner_ != address(0)`. However, `setPriceSigner(address signer)` allows the Safe to update `priceSigner` without checking that `signer != address(0)`:

```solidity
function setPriceSigner(address signer) external {
    if (msg.sender != safe) revert OnlySafe();
    priceSigner = signer;
    emit PriceSignerSet(signer);
}
```

If `priceSigner` is set to `address(0)` (accidentally or during signer rotation), `verifyNote()` in `OakOracle` will unconditionally revert:

```solidity
address signer = priceSigner;
if (signer == address(0) || OakPriceNote.recover(n, sig, msg.sender) != signer) {
    revert NoteBadSignature();
}
```

Because `OakBurner.buyAndBurn` calls `oracle.verifyNote(n, sig, msg.sender)`, all buy-and-burn operations are completely disabled until a non-zero signer is re-set by the Safe.

**Recommendation**

Add a zero-address check to `setPriceSigner`:

```diff
 function setPriceSigner(address signer) external {
     if (msg.sender != safe) revert OnlySafe();
+    if (signer == address(0)) revert InvalidAddress();
     priceSigner = signer;
     emit PriceSignerSet(signer);
 }
```

**Team Response**

Acknowledged.

Acknowledged. A zero signer makes every note fail, but only the owner can set it and the same call restores service, so it is not permanent. It is the intended switch that pauses all note-based actions at once, so we are keeping it. It is now documented as the pause switch.

### [I-11] Gas optimizations and code quality notes

**Severity**

Informational

**Location**

`OakBurner.sol`, `OakSubscription.sol`

**Description**

**OAK-GAS-01: pack `armedAt` and `lastBurnAt` in `OakBurner`.** Both are `uint64` and use separate slots. Packing them into one slot saves about 20,000 gas at deployment and 5,000 gas per disarming burn.

```diff
-uint64 public armedAt;
-uint64 public lastBurnAt;
+uint64 public armedAt;
+uint64 public lastBurnAt; // declare adjacent so both share one slot
```

**OAK-GAS-02: pack the per-user mappings in `OakSubscription`.** `plan`, `paidUntil`, `hasRecord` and `grandfathered` are 5 separate mappings. One struct brings this to 2 slots and saves about 60,000 gas per new subscriber.

```solidity
struct Sub {
    uint64 paidUntil;
    uint8 plan;
    bool hasRecord;
    bool grandfathered;
}
mapping(address => Sub) private subs;
```

**OAK-GAS-03: duplicate `spotOakPerEthE18` in `buyAndBurn`.** The spot price is read once inside `verifyNote` and again in `buyAndBurn`, which costs an extra `poolManager.extsload` staticcall. Return the spot from `verifyNote` and reuse it. Saves about 4,000 gas per burn.

**OAK-GAS-04: redundant allowance reset in `_swapUsdgForWeth`.** The router has already consumed the full allowance, so the second approve is a no-op that costs about 2,900 gas.

```diff
 IERC20(usdg).forceApprove(router, amountIn);
 // swap
-IERC20(usdg).forceApprove(router, 0);
```

**OAK-GAS-05: `Math.mulDiv` for a fixed 5% ceiling in `signupBurn`.** A plain ceiling division is cheaper and cannot overflow here.

```diff
-uint256 burn = Math.mulDiv(amount, 500, 10_000, Math.Rounding.Ceil);
+uint256 burn = (amount * 500 + 9_999) / 10_000;
```

**OAK-INFO-01: dead constant.** `SIGNUP_BURN_BPS = 500` at L37 of `OakSubscription.sol` is never used. Remove it.

```diff
-uint256 private constant SIGNUP_BURN_BPS = 500;
```

**OAK-INFO-02: inconsistent string revert.** `_requireAuthorizationCaller` (L537) uses a string revert while the rest of the contract uses custom errors from `IOakSubscriptionErrors`.

```diff
-require(auth.from == msg.sender, "caller not authorizer");
+if (auth.from != msg.sender) revert CallerNotAuthorizer();
```

**OAK-INFO-03: invariant divergence.** Burning through a transfer to the dead address and burning through `IBurnableERC20.burn()` do not reduce `totalSupply()` the same way. Pick one path and use it consistently, or document the difference.

**Team Response**

Acknowledged.

Acknowledged. GAS-01 is fixed: `armedAt` and `lastBurnAt` now share a storage slot. We measured about 2,000 to 4,800 gas saved per burn; deployment gets slightly more expensive rather than 20,000 gas cheaper. INFO-03: the contracts never send OAK to the dead address, since both burn through the token, and the documentation that said otherwise is corrected (I-04). INFO-01, INFO-02, GAS-02 and GAS-05 concern `OakSubscription`, which has no users because Oak does not offer subscriptions, so it stays unchanged. GAS-03 needs an oracle interface change, and the GAS-04 allowance reset is intentional defense in depth.
