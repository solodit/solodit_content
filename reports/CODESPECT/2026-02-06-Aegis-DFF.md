# Findings

## High Risk

### [H-01] First redeemer takes all unclaimed LP fees when collectFees(...) is not called prior to redemption

**Files:** [`AegisDFF.sol`](https://github.com/labs-solo/AEGIS_DFF/blob/e8d5ed8a07a09a6d36d0c1401e66957540d90093/contracts/AegisDFF.sol#L737), [`AegisDFFRedeemLib.sol`](https://github.com/labs-solo/AEGIS_DFF/blob/e8d5ed8a07a09a6d36d0c1401e66957540d90093/contracts/libraries/AegisDFFRedeemLib.sol#L171)

**Description:**

All redemption functions in the vault (`redeemFromPositions(...)`, `redeem(...)`, and `redeemToOther(...)`) allow users to redeem their vault shares. During redemption, these functions call `_prepareRedemptionTotals(...)`, which invokes `decreaseLiquidity` on Uniswap V4’s `PositionManager` to withdraw the user’s pro-rata share of liquidity.

```solidity
// All redeem functions ultimately call _prepareRedemptionTotals which withdraws from positions:
// - redeemFromPositions() -> AegisDFFRedeemLib.redeemFromPositions() -> _prepareRedemptionTotals()
// - redeem() -> _redeemToAg() -> AegisDFFRedeemLib.redeemToAsset() -> _prepareRedemptionTotals()
// - redeemToOther() -> AegisDFFRedeemLib.redeemToOther() -> _prepareRedemptionTotals()
```

However, when Uniswap V4’s `DECREASE_LIQUIDITY` action is executed, it returns ALL accumulated LP fee for the position to the caller, not just a proportional share. This means the first user to redeem collects 100% of all LP fees that have accrued since the last fee collection, while subsequent redeemers receive zero fees.

**Impact:** A first redeemer extracts all the LP fees, which should be distributed to all shareholders.

**Recommendation:** Call `collectFees(...)` at the beginning of all redemption functions to capture LP fees into the vault’s idle balance before any withdrawal. This ensures fees are distributed proportionally to all redeemers via the `idleShare` calculation rather than going entirely to the first redeemer.

**Status:** Fixed

**Client response:** Fixed: [85a52180b40b83f2e8b8ebc4c5fc3827ed61b8f4](https://github.com/labs-solo/AEGIS_DFF/commit/85a52180b40b83f2e8b8ebc4c5fc3827ed61b8f4)

## Medium Risk

### [M-01] AegisDFF cannot properly handle native ETH pools across multiple flows

**Files:** [`AegisDFFRedeemLib.sol`](https://github.com/labs-solo/AEGIS_DFF/blob/e8d5ed8a07a09a6d36d0c1401e66957540d90093/contracts/libraries/AegisDFFRedeemLib.sol#L410), [`AegisDFF.sol`](https://github.com/labs-solo/AEGIS_DFF/blob/e8d5ed8a07a09a6d36d0c1401e66957540d90093/contracts/AegisDFF.sol#L992)

**Description:**

The AegisDFF vault has multiple issues when handling pools that use native ETH as one of the currencies:

1. Standard `redeem(...)` reverts with native ETH pools. The `_swapToAG(...)` function executes swaps via the Universal Router but does not send ETH value with the call:

```solidity
function _swapToAG(...) private returns (uint256 amountOut) {
    // ...
    uint256 balanceBefore = outputCurrency.balanceOfSelf();
    // @audit Native ETH not sent to router - reverts
    ctx.universalRouter.execute(commands, inputs);
    amountOut = outputCurrency.balanceOfSelf() - balanceBefore;
}
```

When the input currency is native ETH, the transaction reverts because no `msg.value` is passed.

2. `removePool(...)` does not track native ETH in recently deleted tokens. When a pool is removed, the `_addRecentlyDeletedToken(...)` function explicitly skips native ETH:

```solidity
function _addRecentlyDeletedToken(Currency token) private {
    // @audit Native ETH is skipped here
    if (token.isAddressZero() || _isRecentlyDeletedToken(token)) {
        return;
    }
    _recentlyDeletedTokens.push(token);
}
```

This means when a native ETH pool is removed, the ETH remaining in the vault is not tracked in `_recentlyDeletedTokens` and users cannot claim their proportional share during redemption.

**Impact:**

- The standard `redeem(...)` function is completely broken for vaults containing native ETH pools.
- When native ETH pools are removed, the ETH becomes stuck in the vault with no mechanism for users to claim their proportional share.

**Recommendation:**

1. Pass ETH value when calling `universalRouter.execute(...)`.
2. Consider adding ETH as a custom address to the `_recentlyDeletedTokens` array and also update according to that `_transferRecentlyDeletedTokens` function as well.

**Status:** Fixed

**Client response:** Fixed: [7d155c6815a047bedc90da26fff644cb5985ce47](https://github.com/labs-solo/AEGIS_DFF/commit/7d155c6815a047bedc90da26fff644cb5985ce47)

### [M-02] Liquidity recalculation in withdrawAllEngineShares(...) causes DOS for dismantlePositions(...) when price per share exceeds 1

**Files:** [`AegisDFFPositionLib.sol`](https://github.com/labs-solo/AEGIS_DFF/blob/e8d5ed8a07a09a6d36d0c1401e66957540d90093/contracts/libraries/AegisDFFPositionLib.sol#L802-L812)

**Description:**

The `withdrawAllEngineShares(...)` function is invoked during `dismantlePositions(...)` to remove all engine shares from a V2 pool and redeem the underlying value. However, while the function converts vault shares into *liquidity*, the Aegis Engine expects *shares* to be provided during withdrawal. This logic works correctly only when the price per share equals WAD (i.e., `1e18`). If the share price increases due to accumulated fees or interest, the recalculation of redeemable liquidity can exceed the actual share balance, causing the withdrawal to revert.

```solidity
function withdrawAllEngineShares(...) internal {
    uint256 vaultShares = engine.balanceOf(address(this), shareId);
    // ...
    uint256 totalShares = AegisStateLibrary.getTotalSupply(engine, shareId);
    uint256 equityLWad = AegisStateLibrary.getMarketEquity(engine, pid);

    // @audit-issue This recalculation leads to a revert when price per share > 1
    uint256 liquidityToRedeem =
        FullMath.mulDiv(vaultShares, equityLWad, totalShares * 1e18);
}
```

As a result, the computed `liquidityToRedeem` may exceed the amount implicitly represented by `vaultShares`, triggering a revert inside the Aegis Engine.

**Impact:** The `dismantlePositions(...)` function becomes permanently DoS’d for pools where the engine has accrued value beyond the initial deposit. This prevents the owner from successfully closing V2 (engine-backed) pools.

**Recommendation:** Avoid converting shares into liquidity during withdrawal. Instead, pass and redeem `vaultShares` directly, as this is the unit expected by the Aegis Engine and remains consistent regardless of share price appreciation.

**Status:** Fixed

**Client response:** fixed: [d572b9019c967c108c1a57c5a3ebb83e295002a2](https://github.com/labs-solo/AEGIS_DFF/commit/d572b9019c967c108c1a57c5a3ebb83e295002a2)

### [M-03] Redeeming 0 assets doesn’t transfer the recently deleted tokens

**Files:** [`AegisDFF.sol`](https://github.com/labs-solo/AEGIS_DFF/blob/main/contracts/AegisDFF.sol#L909)

**Description:**

The `redeem(...)` and `withdraw(...)` functions that call the `_redeemToAg(...)` function don’t transfer the recently deleted tokens to the user if the withdrawn assets are 0:

```solidity
function _redeemToAg(uint256 shares, address receiver, address owner) internal returns (uint256 assets) {
    // ...
    if (assets == 0) {
        return 0;
    }

    agToken.transfer(receiver, assets);

    // Transfer recently deleted tokens proportionally (no fee for redeem to AG)
    _transferRecentlyDeletedTokens(receiver, shares, supply, netBps);

    emit Redeemed(owner, receiver, shares, Currency.wrap(asset()), assets);

    return assets;
}
```

For example, if all the pools get removed and users should only receive the recently deleted tokens for their redemptions, calling these functions will burn their shares and they will receive nothing. This is handled properly on the other redeem functions.

**Impact:** Users don’t receive their portion of the recently deleted tokens if their withdrawn assets are 0.

**Recommendation:** Consider moving the `_transferRecentlyDeletedTokens(...)` call before the `assets == 0` check.

**Status:** Fixed

**Client response:** Fixed: [bc1b9ef480fac4f8ba6fad91c0542c953e5a7302](https://github.com/labs-solo/AEGIS_DFF/commit/bc1b9ef480fac4f8ba6fad91c0542c953e5a7302)

### [M-04] dismantlePositions(...) function is vulnerable to price manipulation

**Files:** [`AegisDFF.sol`](https://github.com/labs-solo/AEGIS_DFF/blob/e8d5ed8a07a09a6d36d0c1401e66957540d90093/contracts/contracts/AegisDFF.sol#L706)

**Description:**

The `dismantlePositions(...)` function withdraws liquidity from Uniswap V4 positions owned by AegisDFF and returns the funds to the vault’s idle balances. Dismantling these positions is a prerequisite for removing a pool from the AegisDFF vault. However, the function does not enforce any TWAP-based rebalancing or price validation checks. As a result, a malicious actor could temporarily manipulate the pool’s spot price prior to execution, causing the vault to withdraw liquidity at an unfavourable and unintended token ratio from Uniswap V4.

**Impact:** The vault may exit the position using a manipulated price, leading to an imbalanced withdrawal.

**Recommendation:** Consider enforcing a TWAP-based price validation check within the `dismantlePositions(...)`.

**Status:** Fixed

**Client response:** fixed: [85a52180b40b83f2e8b8ebc4c5fc3827ed61b8f4](https://github.com/labs-solo/AEGIS_DFF/commit/85a52180b40b83f2e8b8ebc4c5fc3827ed61b8f4)

## Low Risk

### [L-01] Missing tick spacing adjustment when calculating limit position upper tick during seeding

**Files:** [`AegisDFF.sol`](https://github.com/labs-solo/AEGIS_DFF/blob/e8d5ed8a07a09a6d36d0c1401e66957540d90093/contracts/AegisDFF.sol#L466)

**Description:**

The `seedPool(...)` function creates one-sided limit positions to provide liquidity for the AG token. When AG is token1 (not token0), the function calculates the position’s tick range to be below the current price.

```solidity
if (agIsToken0) {
    // AG is token0, position should be above current price
    tickLower = AegisDFFPositionLib.alignTickToSpacing(tick, tickSpacing, true) + tickSpacing;
    tickUpper = fullRangeUpper;
} else {
    // AG is token1, position should be below current price
    tickLower = fullRangeLower;
    tickUpper = AegisDFFPositionLib.alignTickToSpacing(tick, tickSpacing, false);
}
```

For the token0 case, the code correctly adds `+ tickSpacing` to ensure the position starts one tick spacing above the aligned tick. However, for the token1 case, there is no corresponding `- tickSpacing` adjustment. This inconsistency means the limit position’s upper tick may overlap with the current tick, potentially placing the position partially in-range rather than fully out-of-range.

**Impact:** The limit position may be partially in-range when AG is token1, which could result in immediate conversion of some AG tokens during the seeding process, rather than the intended behaviour of creating a purely one-sided position.

**Recommendation:** Add `- tickSpacing` adjustment for consistency:

```solidity
tickUpper = AegisDFFPositionLib.alignTickToSpacing(tick, tickSpacing, false) - tickSpacing;
```

**Status:** Fixed

**Client response:** fixed: [e7624a71838646bd66ee488fe7f4353b9b15d0a2](https://github.com/labs-solo/AEGIS_DFF/commit/e7624a71838646bd66ee488fe7f4353b9b15d0a2)

### [L-02] The AegisDFF vault is not fully EIP-4626 compliant

**Files:** [`AegisDFF.sol`](https://github.com/labs-solo/AEGIS_DFF/blob/main/contracts/AegisDFF.sol)

**Description:**

The AegisDFF vault has the following features which are not EIP-4626 compliant:

1. The `maxMint(...)` and `maxDeposit(...)` functions must not revert.
2. The `withdraw(...)` function must revert if all of assets cannot be withdrawn (due to withdrawal limit being reached, slippage, the owner not having enough shares, etc).
3. The `withdraw(...)` function should round up to calculate the shares required from the assets.
4. The `redeem(...)` and `withdraw(...)` functions must emit an event named `Withdraw` with the inputs of `(sender, receiver, owner, assets, shares)`.

**Impact:** Other contracts interacting with the AegisDFF vault will expect different behavior than the actual one.

**Recommendation:** Consider implementing the following changes:

1. The functions should return 0 instead of reverting.
2. The `withdraw(...)` function should revert if user’s shares can’t match the requested assets amount.
3. The `mulDivUp` function should be used to calculate the shares from the assets.
4. The withdrawing functions should implement the event mentioned in the report.

**Status:** Acknowledged

**Client response:** We are aware, we did everything in our power to keep it as compliant. Events were removed for contract size requirements but will be readded if possible. If not the AegisWithdraw will have events to show redemptions.

**CODESPECT fix review:** Leaving as Acknowledged

**Client response:** Fixed all except 2: [320eae4292cba1bd40d8f33501e667d4c83363c0](https://github.com/labs-solo/AEGIS_DFF/commit/320eae4292cba1bd40d8f33501e667d4c83363c0) We don’t want to potentially hinder user experience from withdrawals failing. We are not planning to use the standard redeem and withdraw function in our UI but rather our custom functions in AegisWithdrawal that will allow us to more accurately portray withdrawals via static calls and ensure safe withdrawals from slippage protection.

### [L-03] computeTotalAssets() returns incorrect data

**Description:**

The function `computeTotalAssets(...)` is responsible for returning the AG token value of all assets owned by AegisDFF. It has two issues that result in incorrect values being returned. However, the function is intended for view purposes only so the impact is limited:

1. The function does not include outstanding Uniswap V4 claimable fees:

   - Uniswap V4 positions accrue fees on each swap. These fees are collected before each redeem (if the fix for the CODESPECT high-severity issue is applied), meaning users will receive a share of the outstanding fees. However, these values are not included in the total assets owned by the vault.

2. `_v2LiquidityValue(...)` considers only liquidity present in the Engine-owned position:

   - The function `_v2LiquidityValue(...)` leads to incorrect asset calculations because it only considers liquidity currently owned by the Engine in the Uniswap pool. In practice, liquidity is withdrawn when assets are borrowed from the Engine, and accrued interest and fees are also taken into account. The function should instead account for the equity owned by AegisDFF.

**Impact:** Incorrect data returned by this view function can lead to improperly configured slippage protection and may result in losses for users. Additionally, the front end may display inaccurate information.

**Recommendation:** Consider updating the logic to account for outstanding fees and to correctly evaluate the assets and equity owned within AegisEngine.

**Status:** Fixed

**Client response:** Fix: [fc52a9b9f688522bc97f572f8c57469734baba9c](https://github.com/labs-solo/AEGIS_DFF/commit/fc52a9b9f688522bc97f572f8c57469734baba9c)

### [I-02] Missing deadline parameter in AegisWithdrawal redemption functions to execute at outdated vesting rates

**Files:** [`AegisWithdrawal.sol`](https://github.com/labs-solo/AEGIS_DFF/blob/e8d5ed8a07a09a6d36d0c1401e66957540d90093/contracts/AegisWithdrawal.sol#L46)

**Description:**

The AegisWithdrawal contract provides helper functions (`redeemToAg(...)`, `redeemToOther(...)`, `redeemFromPositions(...)`) that burn vested AegisShares and redeem the resulting DFF tokens via the vault. These functions accept a `minAmountOut` for slippage protection but do not accept a deadline parameter.

```solidity
function redeemToAg(
    uint256 shareAmount,
    uint256 minAmountOut
) external nonReentrant returns (uint256 agOut, uint256 dffClaimed) {
    dffClaimed = _claimVestedDff(msg.sender, shareAmount);
    // @audit No deadline - transaction can execute far in the future
    agOut = aegisDff.redeem(
        dffClaimed, msg.sender, address(this), minAmountOut
    );
}
```

The `AegisShares.claimAegisDff(...)` calculates the DFF amount based on the current `redeemablePercent()`, which increases linearly with time. If a transaction is stuck in the mempool, it will execute at a higher vesting percentage than the user intended. The `minAmountOut` was set based on the original vesting rate, so it no longer accurately reflects slippage protection.

**Impact:** A user submitting a redemption transaction may receive a different amount of DFF than expected if the transaction is delayed. Because `redeemablePercent()` increases over time, a delayed transaction claims more DFF from the AegisShares contract, which could disadvantage other shareholders who expected the original vesting schedule.

**Recommendation:** Add a `deadline` parameter to all three redemption functions and revert if `block.timestamp > deadline`.

**Status:** Fixed

**Client response:** These are the difference of seconds even minutes, and minAmountOut is going to have a .3% difference under intended output. This function works properly and deadline is really not necessary.

**CODESPECT fix review:** Will decrease the severity and leave as acknowledged

### [I-03] Redemptions from V2 pools temporarily blocked when AegisEngine pool utilization is high

**Client response:** This is known and can be adjusted in Aegis Engine if needed.

### [I-04] V2 pool removal can be griefed via AegisEngine share transfers

**Description:**

The `_removePool(...)` function checks whether the vault holds any AegisEngine shares before allowing the removal of a V2 pool:

```solidity
function _removePool(PoolId pid) private returns (uint8 idx) {
    AegisTypes.PoolData storage slot = _poolRegistry.getData(pid);
    if (slot.variant == AegisTypes.HookVariant.V2) {
        (uint256 shareBalance,) = AegisDFFAssetLib.v2ShareInfo(pid, aegisEngine);
        // @audit-issue This check can be griefed by transferring shares TO the vault
        if (shareBalance != 0) revert ActivePositions();
    }
    idx = _poolRegistry.remove(pid);
}
```

The check assumes that the vault will only hold AegisEngine shares as a result of legitimate protocol operations. However, AegisEngine shares are ERC6909 tokens and can be transferred freely. An attacker can block V2 pool removal by directly transferring a non-zero amount of engine shares to the vault. As a result, the vault temporarily holds engine shares, causing `_removePool(...)` to revert with `ActivePositions()`.

**Impact:** An attacker can temporarily deny service to the `removePool()` function for any V2 pool at minimal cost. While the owner can recover by calling `dismantlePositions(...)` to clear the shares, the attack can be repeated indefinitely, resulting in a persistent griefing vector.

**Recommendation:** When removing a pool, consider batching the operation with `dismantlePositions(...)` or otherwise ensuring that externally transferred engine shares cannot block pool removal.

**Status:** Fixed

**Client response:** Fixed: [550427de5f46d525f52b7a43aa843a4d0e53900b](https://github.com/labs-solo/AEGIS_DFF/commit/550427de5f46d525f52b7a43aa843a4d0e53900b)

### [I-06] Checks-Effects-Interactions pattern violation in redeemFromPositions(...)

**Original severity:** Best Practices

**Files:** [`AegisDFF.sol`](https://github.com/labs-solo/AEGIS_DFF/blob/e8d5ed8a07a09a6d36d0c1401e66957540d90093/contracts/AegisDFF.sol#L766)

**Description:**

The `redeemFromPositions(...)` function burns the user’s shares after executing the redemption logic, which can involve the native ETH transfer if one of the managed pools contains native ETH.

```solidity
(tokens, amounts) = AegisDFFRedeemLib.redeemFromPositions(ctx, _poolRegistry); // @audit can contain .call if native ETH in the pools
// ... slippage checks ...
_burn(ctx.owner, ctx.shares); // @audit burn AFTER low level call
```

This violates the Checks-Effects-Interactions (CEI) pattern, where state changes (effects) should occur before external calls (interactions). While the `nonReentrant` modifier is present and prevents direct reentrancy, following CEI is a defence-in-depth best practice.

**Impact:** No direct exploit identified due to `nonReentrant` modifier protection.

**Recommendation:** Move `_burn(ctx.owner, ctx.shares)` before the `AegisDFFRedeemLib.redeemFromPositions(...)` call to follow CEI pattern.

**Status:** Fixed

**Client response:** Fixed: [660471d90aa4aa052276651e4557facf70bbe6e4](https://github.com/labs-solo/AEGIS_DFF/commit/660471d90aa4aa052276651e4557facf70bbe6e4)

### [I-07] Use Ownable2Step instead of Ownable for safer ownership transfers

**Original severity:** Best Practices

**Files:** [`AegisDFF.sol`](https://github.com/labs-solo/AEGIS_DFF/blob/e8d5ed8a07a09a6d36d0c1401e66957540d90093/contracts/AegisDFF.sol#L52)

**Description:**

The AegisDFF contract inherits from OpenZeppelin’s `Ownable` for access control. The standard `Ownable` pattern allows direct ownership transfer via `transferOwnership(newOwner)`, which immediately grants ownership to the specified address.

```solidity
contract AegisDFF is ERC4626, Ownable, ReentrancyGuard, IERC721Receiver, IAegisErrors, IAegisDFF {
```

If an incorrect address is provided (typo, wrong network address, or zero address), ownership is irrevocably lost. `Ownable2Step` mitigates this by requiring the new owner to explicitly accept the transfer via `acceptOwnership()`. This would make the vault’s administrative capabilities more secure.

**Recommendation:** Consider replacing `Ownable` with a two-step transfer of ownership.

**Status:** Fixed

**Client response:** Will be owned by a safe that requires 4 signatures to mitigate such scenario, will change to Ownable2Step if we can fit it into contract size.

**Client response:** Added Ownable2Step: [bb06957451f00a0604a81990c8288f371857276e](https://github.com/labs-solo/AEGIS_DFF/commit/bb06957451f00a0604a81990c8288f371857276e)

**Client response:** Fixed for AegisShares and AegisWithdraw: [0481902edd93f1aa37e3a1b661d2280df2c9e1d5](https://github.com/labs-solo/AEGIS_DFF/commit/0481902edd93f1aa37e3a1b661d2280df2c9e1d5)
